# 11장 백엔드 서비스 이해하기

백엔드는 사용자에게 보이지 않는 데이터 처리와 보안을 담당하는 영역으로, AWS는 EC2 오토스케일링, ECS, 다이나모DB, API 게이트웨이, 람다, 탄력적 로드 밸런서 등을 백엔드 서비스로 제공함. 그중 탄력적 로드 밸런서(ELB)는 사용자가 급증하더라도 트래픽을 적절하게 분산해 서버를 안정적으로 운영하게 해주는 부하 분산 서비스임.

### 11.1 로드 밸런서 유형과 동작 방식

로드 밸런서 유형에 따라 부하 분산이 이루어지는 계층이 결정됨.

- **ALB(응용 계층, 7계층):** HTTP 혹은 HTTPS 트래픽을 라우팅하며, 경로 기반 라우팅 같은 고급 웹 기능을 제공함.
- **NLB(전송 계층, 4계층):** TCP 혹은 UDP 트래픽을 라우팅함. ALB와 달리 고정 IP를 사용할 수 있어, 연결 대상을 IP로 제한해야 하는 상황에 유용함.
- **GWLB(네트워크 계층, 3계층):** 2020년 11월에 추가된 유형으로, 주로 타사 제품을 AWS로 마이그레이션할 때 사용되며 웹사이트 구축 용도로는 적합하지 않음.
- **로드 밸런서 노드:** 로드 밸런서를 생성하면 선택한 서브넷에 노드가 생성되고, 이 노드로 각 가용 영역을 구분해 부하 분산을 수행함. 따라서 인터넷을 통해 웹 서비스를 공개하려면 퍼블릭 서브넷을, 사내에서만 사용할 것이라면 프라이빗 서브넷을 선택해야 함.

### 11.2 대상 그룹과 리스너

로드 밸런서 노드는 가용 영역을 구분하는 용도일 뿐, 부하 분산할 EC2 인스턴스를 선택할 수는 없음. 이 문제를 해결하는 것이 대상 그룹과 리스너임.

- **대상 그룹(Target Group):** 로드 밸런서 노드와 EC2 인스턴스 사이의 중간 다리 역할을 하며, 부하 분산을 시도할 EC2 인스턴스를 등록하고 관리함. 지정한 포트로 상태 확인(Health Check)을 수행해 정상이면 healthy, 비정상이면 unhealthy를 반환함.
- **리스너(Listener):** n개의 대상 그룹을 운영할 때 어떤 방식으로 접근할지 설정하는 기능임. 리스너 규칙에서 프로토콜과 포트를 지정해 대상 그룹을 연결지을 수 있음.
- **리스너 규칙:** HTTPS:443, HTTPS:444처럼 포트로 구분하는 포트 기반 라우팅, `/web`과 `/api`처럼 경로로 구분하는 경로 기반 라우팅, 잘못된 URL이나 점검 중인 상황에서 응답 코드와 텍스트를 반환하는 고정 응답 반환 규칙이 자주 사용됨.
- **SSL/TLS 인증서:** HTTPS(443)나 TLS를 사용하려면 암호화된 연결이 필요하므로 AWS ACM에서 인증서를 발급받아 로드 밸런서에 등록함. 이때 EC2 인스턴스와는 HTTP 80번 포트로 통신하더라도 사용자는 HTTPS로 안전하게 접속할 수 있음.

### 11.3 부하 분산 알고리즘

- **라운드 로빈:** 받은 요청을 대상 서버에 순서대로 할당함. 대상 서버의 성능이 동일하고 처리 시간이 짧을 때 주로 사용함.
- **가중치 랜덤:** 정상 작동하는 서버에 임의의 순서로 요청을 라우팅함. ATW(Automatic Target Weights)와 함께 동작해 장애나 성능 저하를 감지하면 자동으로 다른 서버로 트래픽을 전달함.
- **최소 미해결 요청:** 현재 연결 수가 가장 적은 서버로 라우팅하는 동적 알고리즘임.
- **교차 영역 로드 밸런싱:** 위 알고리즘은 ALB에서 사용되며, NLB는 AWS 하이퍼플레인이라는 독자적인 기술을 사용함. 교차 영역 로드 밸런싱은 ALB에서 항상 유효화되어 있지만, NLB는 기본적으로 무효화되어 있어 가용 영역별 균등 분산을 원한다면 별도로 설정해야 함.

### 11.4 환경별 로드 밸런서 구성 패턴

실전 환경과 개발 환경을 나누어 운영할 때는 두 가지 패턴을 고려할 수 있음.

- **환경별로 나누는 패턴:** 개발 환경의 문제가 실전 환경에 영향을 주지 않고, 트래픽과 리소스 사용률을 분리해 관리할 수 있으며, 환경별로 액세스 제어 정책과 확장을 독립적으로 적용할 수 있는 가장 이상적인 패턴임.
- **하나로 제어하는 패턴:** 포트 기반 혹은 경로 기반 라우팅으로 두 환경을 구분함. 리스너 규칙이 복잡해지고 로드 밸런서 장애 시 두 환경 모두가 영향을 받으므로, 같은 환경 내에서 여러 경로로 나누고 싶을 때 사용하는 것이 좋음.

## 12장 클라우드 서버 최적화를 위한 백엔드 서비스 파악하기

아마존 EC2 오토스케일링은 스케일업(사양 업그레이드), 스케일아웃(같은 사양의 서버 추가), 스케일인(불필요한 서버 삭제)을 조절해 클라우드 서버를 최적화하는 서비스임.

### 12.1 시작 템플릿과 오토스케일링 그룹

오토스케일링 그룹을 생성하려면 먼저 AMI, 인스턴스 유형, EBS 볼륨, 네트워크 설정 등을 담은 시작 템플릿이 필요함. 시작 템플릿은 복수의 버전으로 관리할 수 있어, 서로 다른 설정의 버전을 만들어 상황에 맞게 그룹에 적용할 수 있음.

- **원하는 용량:** 오토스케일링 그룹을 만들 때 생성할 초기 EC2 인스턴스 수임.
- **최소 용량:** 수동이든 자동이든 이보다 적게 만들 수 없음. 인스턴스를 삭제해도 최소 용량을 유지하고자 새 인스턴스가 생성됨.
- **최대 용량:** 수동이든 자동이든 이 값을 초과해 인스턴스를 늘릴 수 없음.

### 12.2 로드 밸런서와의 상태 확인 차이

오토스케일링 그룹은 확장성과 가용성을 고려해 로드 밸런서와 함께 사용하는 것이 권장됨. 두 서비스의 상태 확인은 결과 처리 방식이 다름.

- **로드 밸런서만 사용:** unhealthy가 발생해도 EC2 인스턴스의 교체 작업은 이루어지지 않음.
- **오토스케일링 그룹과 연결:** unhealthy가 발생한 인스턴스를 그룹에서 제외시키고 새로운 인스턴스를 가동해 그룹에 추가함. 이때 빠져나온 인스턴스는 삭제되지 않고 하나의 EC2 인스턴스로 분류됨.

### 12.3 오토스케일링 그룹 스케일 정책

- **대상 추적 크기 조정:** 평균 CPU 사용률, 평균 네트워크 입력/출력, 대상당 ALB 요청 수 중 하나를 선택해 해당 지표를 기준으로 스케일링함.
- **단계 크기 조정:** 클라우드워치 경보를 기반으로 스케일링하며, 추가하거나 삭제할 인스턴스 수를 설정할 수 있음.
- **단순 크기 조정:** 클라우드워치 경보 기반이지만 다음 스케일링까지 대기 시간이 존재함. 트래픽에 빠르게 대응해야 하는 만큼 현재는 사용이 권장되지 않음.
- **예측 크기 조정:** 머신러닝으로 클라우드워치의 24시간 기록을 분석해 향후 수요를 미리 예측함. 동적 크기 조정 정책과 함께 사용하면 더 최적의 정책을 구성할 수 있음.
- **예약된 작업:** 지정한 날짜와 시간에 스케일링을 실시하며, 매일·매주 같은 반복 설정도 가능함.

### 12.4 오토스케일링 그룹과 AMI

오토스케일링 그룹은 생성 시 설정한 값을 바탕으로 인스턴스를 만들기 때문에, 사용자가 수동으로 설치한 소프트웨어는 스케일 작업으로 새로 생성된 인스턴스에 적용되지 않음. 따라서 소프트웨어를 설치한 인스턴스의 AMI를 생성하고, 오토스케일링 그룹의 AMI를 이 AMI로 교체하는 방식으로 해결함. 즉, 오토스케일링 그룹을 사용할 때는 AMI를 어떻게 활용할지 고민하는 것이 중요함.

## 13장 컨테이너를 위한 백엔드 서비스 파악하기

아마존 ECS(Elastic Container Service)는 AWS에서 도커 컨테이너를 배포하고 운영, 관리하는 완전 관리형 컨테이너 서비스임. 도커는 윈도우에서는 동작하지만 우분투에서는 동작하지 않는 것과 같은 환경 불일치를 해결하는 오픈 소스 프로젝트로, 도커파일을 빌드하면 정적인 도커 이미지가 되고 이 이미지를 실행하면 동적인 컨테이너가 됨.

### 13.1 아마존 ECR과 작업 정의

- **아마존 ECR(Elastic Container Registry):** 정적인 도커 이미지를 보관하는 서비스임. 리포지토리는 IAM 등 특정 권한을 가진 사용자만 사용하는 프라이빗과 누구나 사용할 수 있는 퍼블릭으로 나뉘며, 생성 후에는 재설정이 불가능하므로 목적을 명확히 하고 설정해야 함.
- **작업 정의(task definition):** ECR의 이미지를 비롯한 컨테이너의 전체적인 구성을 정의하는 작업으로, 작업 이름, 컨테이너 이름, 사용할 이미지, 포트 번호, 환경 변수, 볼륨, 실행 역할, 네트워크 모드 등이 포함됨.

### 13.2 네트워크 모드

- **호스트:** 호스트의 ENI를 사용해 통신하며, 호스트에서 사용하는 포트가 곧 컨테이너 포트가 됨. 컨테이너의 네트워크 네임스페이스가 호스트와 공유되어 이미 사용 중인 포트를 중복해서 사용할 수 없으며, 로드 밸런서를 통한 부하 분산이 불가능함.
- **브리지:** 브리지의 동적 매핑 기능으로 호스트 포트와 컨테이너 포트를 별도로 지정할 수 있음. 호스트 포트를 0으로 지정하면 에페메랄 포트(32768~61000)에서 동적으로 매핑되지만, 포트 제어가 어려워지므로 주의가 필요함.
- **awsvpc:** 각 컨테이너마다 ENI를 생성하며, VPC 내에서 자체 사설 IP가 할당됨. 컨테이너별 보안 설정이 가능해 가장 유연하지만, 생성할 수 있는 ENI 수에 제한이 있음.
- **없음:** 포트 매핑과 외부 연결이 모두 차단됨. 네트워크 기능이 불필요할 때 사용함.

### 13.3 작업, 서비스, 클러스터

- **작업(Task):** 작업 정의를 기반으로 시작한 컨테이너의 모음임. 엔진엑스와 마리아DB처럼 여러 컨테이너를 단일 작업 내에서 실행시킬 수도 있음.
- **서비스(Service):** 작업을 관리함. 작업 수를 2로 설정했다면 하나가 실패하더라도 자동으로 새 작업을 시작해 항상 2가 유지되도록 함. 컨테이너의 시작 유형과 보안 그룹, VPC, 서브넷도 여기서 선택함.
- **클러스터(Cluster):** 서비스와 작업을 포함하는 컨테이너 관리 및 배포를 위한 컴퓨팅 자원의 집합임.
- **시작 유형:** EC2 인스턴스와 파게이트 중 선택할 수 있음. 파게이트는 컨테이너를 서버리스로 실행할 수 있게 해주며, 필요한 리소스를 자동으로 관리하고 실행 환경을 프로비저닝하므로 운영체제 관리나 운용 보수를 신경 쓰지 않고 애플리케이션에만 집중할 수 있음.

## 14장 이벤트 기반 코드 실행 백엔드 서비스 파악하기

AWS 람다는 서버를 구축하지 않고도 작성한 코드를 실행할 수 있는 이벤트 구동형 프로그램 실행 환경임. 넓은 의미로는 서버리스이며, 더 명확하게는 FaaS(Functions-as-a-Service)로 표현할 수 있음.

### 14.1 클라우드 서비스 모델 구분

- **IaaS:** 스토리지, 네트워크, 서버와 같은 하드웨어 리소스를 제공함. 대표적으로 아마존 EC2가 있음.
- **PaaS:** 애플리케이션을 개발하고 테스트, 배포하기 위한 환경을 제공함. AWS 엘라스틱 빈스토크, 아마존 S3가 이에 해당함.
- **SaaS:** 최종 사용자를 위한 소프트웨어로, 구글 닥스와 같은 서비스가 해당함.
- **FaaS:** 개별 함수를 클라우드에서 실행하는 서버리스 아키텍처로, 개발자는 특정 이벤트가 발생할 때 실행되는 함수만 작성하면 됨.

### 14.2 AWS 람다의 이점과 구성

람다는 코드 실행 시간과 요청 수에 따라 비용이 청구되므로, 이벤트가 많지만 실행 시간이 짧을 때 비용을 크게 절감할 수 있음. 그 외에도 AWS가 실행 환경을 관리해주는 안전한 실행 환경, 장애 위험 부담 감소, 다양한 프로그래밍 언어 제공, 다른 AWS 서비스와의 연동이라는 이점이 있음.

- **함수 생성 유형:** 새로 작성, 블루프린트 사용, 컨테이너 이미지 세 가지가 있음. 블루프린트는 샘플 코드를 제공받아 더 간편하게 함수를 작성할 수 있음.
- **함수 구성:** 함수 이름, 런타임(.NET 8, 자바 21, Node.js 22.x, 파이썬 3.13 등), 아키텍처(x86_64, arm64), 권한으로 구성됨.
- **권한:** 다른 AWS 서비스와 연동하려면 IAM으로 필요한 권한을 부여해야 함.

## 15장 API 관리를 위한 백엔드 서비스 파악하기

아마존 API 게이트웨이는 API를 간편하게 구축하고 게시하고 모니터링할 수 있게 돕는 완전 관리형 서비스임. 게이트웨이를 사용하지 않으면 애플리케이션이 결제, 장바구니, 주문 목록, 재고 관리 API와 각각 개별 통신을 수행해야 하지만, 게이트웨이를 두면 애플리케이션은 게이트웨이하고만 통신하면 되므로 API 남용을 방지하고 개발자의 부담을 줄일 수 있음.

### 15.1 API 게이트웨이의 장단점

- **장점:** 다양한 버전을 최소한의 노력으로 테스트할 수 있는 효율적인 API 개발, API 호출 정보·오류율·대기 시간을 실시간으로 확인하는 간편한 모니터링, 무료 티어가 제공되는 비용 구조, 클라우드프론트와 통합되어 최적의 대기 시간을 제공하는 생산성이 있음.
- **단점:** 모든 API를 통합해 처리하므로 게이트웨이에 문제가 발생하면 전체 API의 동작이 멈추게 됨. 또한 타사 API를 사용하는 경우 해당 API의 보안에 개발자가 직접 관여할 수 없음.

### 15.2 API 유형

- **REST API:** REST 규칙으로 만든 API로, 리소스를 생성하거나 검색하고 업데이트 및 삭제하는 작업에 적합함.
- **REST API 프라이빗:** REST API와 동일하지만 VPC 내에서만 접근할 수 있도록 제한된 API임.
- **HTTP API:** REST의 네 가지 원칙을 반드시 적용하지 않는 API로, REST API에 비해 대기 시간이 짧고 비용 효율적임.
- **웹소켓 API:** 양방향 통신 프로토콜로, 하나의 TCP 연결로 송신과 수신을 동시에 실시할 수 있음. 채팅이나 게임처럼 실시간성이 요구될 때 적합함.

### 15.3 REST의 네 가지 원칙

- **주소 가능성:** 제공하는 정보가 URI를 통해 표현될 수 있으며, 각 정보는 고유한 URI를 가짐.
- **상태 비저장:** 정보를 교환할 때 상태를 유지하지 않고 요청과 응답을 한 번만 사용해 완료함. 반대로 상태 저장은 상태를 유지해 연속적인 상호작용을 가능하게 함.
- **연결성:** 정보 내에 다른 리소스에 대한 링크가 포함되어 서로 상호 작용이 가능함.
- **통일 인터페이스:** 미리 정의한 공유 방식을 의미하며, 대표적으로 HTTP 메서드(GET, PUT, POST, DELETE)가 있음.

## 16장 유연한 NoSQL 데이터베이스 서비스 파악하기

아마존 다이나모DB는 AWS가 제공하는 NoSQL 데이터베이스로, SQL을 사용하지 않고 고정된 스키마도 없으며 데이터를 키-밸류 형식이나 JSON 형식으로 저장함. 완전 관리형이고, 세 개의 가용 영역에 자동으로 데이터를 복제하며, 용량 계획 없이 사용한 만큼만 지불하는 서버리스 모델로 운영할 수 있음.

### 16.1 아마존 RDS와의 차이

아마존 RDS는 VPC를 설계하고 구축해야 하며 그 내부에 생성되지만, 다이나모DB는 VPC 설계 없이도 리전 단위로 생성되고 관리됨. OS 패치 같은 정기 유지보수도 AWS가 직접 처리하므로 서버리스의 장점을 최대한 살릴 수 있음.

- **유형:** 다이나모DB는 NoSQL, RDS는 SQL임.
- **검색 조건:** 다이나모DB는 사전에 지정된 키 또는 인덱스로만 검색이 가능하지만, RDS는 SQL문으로 자유롭게 검색할 수 있음.
- **검색 처리:** 다이나모DB는 JOIN 연산을 지원하지 않아 복잡한 검색 처리를 할 수 없고, RDS는 JOIN을 통한 복잡한 검색 처리가 가능함.
- **확장성:** 다이나모DB는 높은 확장성을 제공해 많은 양의 트래픽을 처리할 수 있고, RDS는 쿼리 처리는 뛰어나지만 리드 복제본 생성 등 스케일에 대한 추가 설정이 필요함.
- **사용 사례:** 다이나모DB는 실시간·모바일 애플리케이션 및 IoT 디바이스의 데이터 관리에 적합하고, RDS는 복잡한 관계와 일관된 트랜잭션 처리가 필요한 비즈니스 및 금융 시스템에 적합함.

### 16.2 다이나모DB의 제약

다이나모DB는 키밸류 형태의 NoSQL이므로 대규모 데이터 분석에 적합한 OLAP에는 어울리지 않고, 소규모 데이터를 대량으로 처리하는 OLTP에 적합함.

- **트랜잭션 제약:** 단일 트랜잭션 내의 개별 작업을 최대 100건까지만 설정할 수 있어, 수천 혹은 수백만 건을 처리하는 RDS에 비하면 적은 처리 양임.
- **검색 조건의 유연성 제약:** 인덱스 구조에 크게 의존하므로 SQL처럼 복잡한 쿼리 패턴을 처리하는 데 제약이 있음.
- **JOIN 제약:** 테이블 간 JOIN을 할 수 없어, 여러 번 쿼리를 실행하거나 단일 테이블에 항목을 정리하는 싱글 테이블 설계가 필요함.
- **항목 크기:** 항목당 크기 상한이 400KB이므로 큰 데이터를 직접 저장하는 용도로는 적합하지 않음.

### 16.3 파티션 키와 보조 인덱스

다이나모DB의 데이터는 여러 파티션에 분산되어 저장되며, 어느 파티션에 저장되는지는 파티션 키로 결정됨. 정렬 키가 설정된 경우 파티션 내에서 정렬 키를 기준으로 정렬되어 물리적으로 가깝게 배치되고, 기본키는 파티션 키 또는 파티션 키와 정렬 키의 복합 키를 의미함.

- **글로벌 보조 인덱스:** 어느 한 테이블을 바탕으로 다른 파티션 키와 정렬 키를 지정해 테이블을 작성하는 구조임. 테이블 작성 후에도 설정할 수 있음.
- **로컬 보조 인덱스:** 파티션 키는 유지하며 다른 정렬 키만 지정해 테이블을 작성함. 테이블을 생성할 때 설정해야 함.

### 16.4 엑셀러레이터와 용량 모드

- **다이나모DB 엑셀러레이터(DAX):** 다이나모DB와 호환되는 완전 관리형 인메모리 캐시 서비스임. 캐시가 있으면 바로 반환하고, 없으면 다이나모DB에 요청해 받은 결과를 캐시에 보존한 뒤 반환하여 밀리초에서 마이크로초로 퍼포먼스를 올림.
- **온디맨드 모드:** 읽기 및 쓰기 용량을 설정하지 않고 자동으로 스케일링하므로 트래픽을 예측할 수 없을 때 유용함.
- **프로비저닝 모드:** 읽기와 쓰기 용량을 설정해 그 값을 상한으로 트래픽을 처리함. 트래픽을 예측할 수 있을 때 유용하며 오토스케일링으로 용량을 자동 조정할 수 있음.
- **가용성과 내구성:** 기본적으로 다중 AZ를 지원해 같은 리전 내 3개의 가용 영역 간 데이터가 실시간으로 복제되며, 글로벌 테이블을 생성하면 다중 리전에 걸쳐 테이블을 복제해 사용자가 어디에 있든 낮은 대기 시간으로 데이터를 제공할 수 있음.
